GitHub Pages supports a custom subdomain such as blog.example.com, and GitHub recommends subdomains because they can use a stable DNS CNAME. 

Why not hardwarewrighter.com/blog directly?
DNS maps hostnames, not URL paths.

It can route:

hardwarewrighter.com
blog.hardwarewrighter.com
www.hardwarewrighter.com
It cannot independently route:

hardwarewrighter.com/blog
to GitHub Pages while leaving the rest of hardwarewrighter.com parked elsewhere.

Furthermore, GitHub Pages custom-domain configuration accepts an apex domain or subdomain—not a domain plus a path. Supported forms include example.com, www.example.com, and blog.example.com. 

Therefore this will not work as a Pages custom domain:

hardwarewrighter.com/blog
But these will:

hardwarewrighter.com
www.hardwarewrighter.com
blog.hardwarewrighter.com

A generic workflow looks like this:

name: Deploy blog

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Configure Pages
        uses: actions/configure-pages@v5

      # Replace this with the selected generator's build commands.
      - name: Build site
        run: |
          ./scripts/build

      - name: Upload Pages artifact
        uses: actions/upload-pages-artifact@v4
        with:
          path: ./dist

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    runs-on: ubuntu-latest
    needs: build

    steps:
      - name: Deploy Pages
        id: deployment
        uses: actions/deploy-pages@v4

Getting an exact /blog URL
You have three realistic options.

Option 1 — Redirect /blog to the subdomain
hardwarewrighter.com/blog
    → 301 redirect
blog.hardwarewrighter.com/
Benefits
Simplest

GitHub Pages remains directly supported

No proxy complexity

Search engines understand the permanent redirect

Apex site and blog can be hosted independently

Limitation
The browser ultimately displays:

blog.hardwarewrighter.com
This is my recommendation.

Option 2 — Reverse-proxy /blog
Host hardwarewrighter.com through something capable of path routing, such as:

Cloudflare Workers

Cloudflare Pages with a Worker

Netlify

Vercel

Your own nginx/Caddy server

Then route:

hardwarewrighter.com/blog/*
to the GitHub Pages site.

Conceptually:

hardwarewrighter.com/blog/cor24-tb/
        ↓
proxy
        ↓
blog.hardwarewrighter.com/cor24-tb/
Benefits
Browser retains the exact /blog address

Apex site can contain other sections

Risks
Asset and canonical URLs must use /blog/ as their base

Generated links must be path-aware

Search indexes, RSS URLs, CSS, JavaScript, images, and pagination must all account for the prefix

GitHub Pages HTTPS/CDN is now behind your proxy

More places can fail

A redirect is much less fragile than a reverse proxy.

Option 3 — Use GitHub’s organization-site inheritance
GitHub supports a custom domain on an organization site and can place project sites beneath it. For example, if the organization site uses www.example.com, a repository called blog can appear beneath it as www.example.com/blog. 

That would require:

hardwarewrighter/hardwarewrighter.github.io
hardwarewrighter/blog

https://hardwarewrighter.com/blog/

hardwarewrighter.github.io
organization-site repository—the thing you were hoping to avoid. It also means the apex-domain Pages configuration affects the organization’s other project sites.

This architecture is valid, but I would not choose it merely to avoid using a blog subdomain.
